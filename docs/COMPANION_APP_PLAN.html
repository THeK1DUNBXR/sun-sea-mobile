Delivery plan · Sun Sea SaaS · part five

Two prototypes exist. The plan makes them one product.

A companion app strategy for Sun Sea, reconciled against the 95-item backlog and against what the sun-sea-mobile repository already runs on a phone: a field-sales app, a founder's dashboard, and a backend extension the ERP has not yet absorbed.

Built 2 apps · 35 screens · ~9,000 lines · 2 CI pipelines · 7 APK releasesBacklog touched S1, S3–S6, PC4, PL2–PL4, HR1, HR5, M4, M6, MES2, WM3, ES2, FI5Basis repo measured directly · sizes on part three's scale

The companion app is not one app; it is one codebase with four roles, and the first two roles are already prototyped. The field-sales app (Sun Sea Field, v1.1) captures collections, orders, visits, follow-ups, expenses and new outlets offline and syncs them through a backend extension written against the real schema. The founder's app (Sun Sea Insights, v0.2) reads the business the way the management TV wall does. Both install from GitHub Releases today.

What separates a prototype from a product is unglamorous: the backend extension has to be merged behind Phase 0's tenancy, sync needs conflict rules that are tested rather than assumed, the APK is signed with a debug key, there is no over-the-air update path, no crash reporting, no end-to-end test, and login is a password with no second factor. That work is about seven developer-weeks and it comes first. The supervisor and store roles, and a customer app, follow the ERP phases they depend on.

What this changes in the backlog

Four part-three items are further along than the Build Plan assumes because the field app exists. S1 (real field-sales GPS, L · 3 weeks) is largely the Field app plus a position feed for the TV wall — about 1.5 weeks remain. PC4 (offline-first sync, L · 3 weeks) has its engine; what remains is conflict rules under test and the tenancy backfill, about 1 week. HR1's attendance gets a second, cheaper source: the agent's day start. And the founder's app is the first consumer of PF5's public read surface, which argues for building that surface as read-only aggregation endpoints in Phase 1 rather than a full platform in Phase 4.

What the market says a companion app must do

Sources at the end. Summarised to the points that changed a decision below.

  • Offline is the normal case, not the edge. Field guides converge on local-first storage, an outbox with idempotency keys, delta sync, tombstones and explicit conflict policy per table. Most data loss in field apps comes from "last write wins" applied to records that two people legitimately edit. The Field app already has the outbox and delta pull; it does not yet have written conflict rules or tests for them.
  • Security is a level, not a feature. OWASP MASVS gives a testable baseline (L1 for most apps, L2 where payments or regulated data flow). DPDP's Rule 6 safeguards apply to a device that carries 500 customers' phones and balances. The concrete asks: no secrets in the bundle, tokens in the OS keystore, short-lived access tokens with server-side revocation per device, a second factor for login, consent for location and camera, erase-on-logout.
  • Ship JavaScript without waiting for a store review. Over-the-air updates on Expo's protocol are the industry default for React Native, either hosted (EAS Update) or self-hosted on the Expo Updates protocol. For a product whose tenancy and PII posture is being certified, self-hosting keeps the update server inside the same boundary as the ERP.
  • Test on a device, in CI. Maestro's YAML flows run on an emulator in GitHub Actions with low flakiness and no native instrumentation; Detox earns its setup cost only for deep synchronisation cases such as offline sync and biometric prompts. The ERP's own Phase 0 test discipline should extend to the app.
  • Supervisors want alerts, not dashboards. Shop-floor mobile products lead with andon-style push alerts (line stopped, downtime running, quality hold) and short capture forms, with the dashboard second. That shapes the supervisor role below.
  • Field-sales practice (already researched for v1.1): beat discipline, promise-to-pay, instant digital receipts, end-of-day cash control, targets and nudges, a customer 360 at the doorstep. Built.

The decision: one codebase, four roles

Today there are two Expo apps with two package names and two release pipelines. That was right for prototypes that had to be evaluated separately. It is wrong for a product: two logins, two MFA enrolments, two OTA channels, two Play listings per tenant, and a UI kit that has already forked twice.

Recommendation: a single repository with a shared core and role modules, shipped as one installable app. The user's role from the ERP's own permission registry decides which modules appear after login — a founder sees Insights, an agent sees Field, a supervisor sees the plant module, and a person with two roles sees both. The founder's TV-style theme becomes the Manager module's theme rather than a separate binary.

Where a second binary still makes sense

A customer / retailer app is a different audience with a different trust boundary (a customer must never hold a session that can read another customer) and different distribution (public Play listing, marketing). It stays a separate, much smaller app — or, more likely for the first year, a WhatsApp-first flow plus the S4 web portal with FI5 payment links, and no app at all until customers ask.

Sync, made honest

PC4 is "offline-first mobile sync". The engine exists; the rules do not.

The Field app pulls changed rows by updated_at per table and pushes its outbox with device-generated UUIDs, so a retried push is idempotent. That is the right shape. What a product needs on top is a written policy per table, enforced on the server and tested with a cross-device suite:

TableWho owns itOn conflictWhy
customers, invoices, products, routesERPserver wins, alwaysMasters and ledgers are never edited on the device. The app shows stale-by-N-minutes, never a local edit.
collections, orders, expenses, handovers, leadsdevice (create-only)append; server assigns numbersDevice creates, server posts and stamps receipt / order / expense numbers back. A duplicate UUID is a no-op, not a second receipt.
visits, follow-ups, day sessionssharedfield-level merge, latest updated_at per field, server tie-breakAn office user can re-plan a visit while the agent checks in. Merging by field keeps both; a whole-row overwrite loses one.
attachmentsdeviceupload once, URL stamped on parentPhotos survive app restarts because the queue is a table, not memory.
deleted rowseithertombstones in pull, 30-day retentionWithout tombstones a cancelled visit lives forever on a phone that was offline that day.

Three more rules belong in the contract: every push carries the device id and app version; the server rejects a push from a device the tenant has revoked; and a clock skew above five minutes is reported to the user rather than silently reordering events.
